# R2: Verifier Ablation, Pre-registration

**Written 24 October 2026, before any arm C generation exists.** Roadmap task R2
(`COMPARISON WITH EXISTING SYSTEMS/ROADMAP.md`).

## Question

How many incorrect claims would reach a reader if the grammar, the verifier or both were removed?
Whether generation succeeds is not the measure.

## Data

- **Nights:** the 31 dev packets (`distillation/results/phase2_dev_packets`), the dev manifest only.
- **Test set:** not touched. The runner refuses test packets.

## Arms

| Arm | Generation | Release rule |
|---|---|---|
| **A** | grammar on (`report/claims.gbnf`) | the frozen verifier gates: a report is released only with zero violations |
| **B** | **the same generations as A** | no gate: every claim the model wrote is released |
| **C** | grammar off (the 2G "unconstrained" arm: exactly `--grammar-file` removed) | no gate |

All other settings are the frozen evaluation's:
- `llama-completion` b10927, prompt P1, temperature 0, seed 0;
- n_predict 3,000, context 12,288;
- the pinned Llama chat template;
- one generation per packet, no retries.

## Models

- **Primary:** Llama-3.2-3B-Student (the v1 report model).
  - Arms A and B: its existing cached dev generations, `candidates/cache/Llama-Student/P1`.
  - Arm C: generated by this task, into this folder's `cache/`.
- **Secondary:** Llama-3.2-3B-Instruct (untrained base).
  - Arms A and B: `candidates/cache/Llama-3.2-3B-Instruct/P1`.
  - Arm C: `.../P1-nogrammar`.
  - These caches already exist from the 2G ablation, so no new generation is needed.

## Scorer

The frozen verifier (`report.verify_report`) is the scorer in **every** arm. In arm A it also decides
release; in B and C it only labels what would have been released.

## Measures, per arm

**1. Released reports.**
- Arm A: verifier pass.
- Arms B and C: every output.
- An arm C output that isn't a parseable JSON array counts as a **malformed release**: in an ungated
  system, the raw text would reach the reader.

**2. Incorrect released claims,** by category. A claim is counted once per category, by the codes the
verifier attaches to its `claim_id`.

| Category | Codes |
|---|---|
| Wrong number | `L2.value_mismatch`, `L2.unit_mismatch` |
| Wrong or missing evidence | `L1.unknown_evidence_id`, `L1.bad_cites_arity`, `L2.cited_id_not_in_packet`, `L2.uncited_quantity`, `L2.not_associative_evidence` |
| Unreliable stated as fact | `L2.unsafe_item_not_hedged` |
| Reliable hedged | `L2.safe_item_hedged` |
| Other rule breaks | every other L1/L2 code attached to a claim |

**3. Report-level failures among released reports:**
- missing any of the 5 mandatory items;
- report-level violations with no `claim_id` (for example `L2.missing_review_flag`).

**4. Headline:** released reports containing at least one incorrect claim, a malformed output, or a
missing mandatory item, out of 31.

**5. Also reported:**
- numeric fidelity (exact value matches / value claims);
- arm C token-limit hits.

## Expectations, stated in advance

- **Arm A:** 0 incorrect released claims, by construction.
- **Arm B (Student):** dev was 30/31 at 5/5, with violations on one packet. So arm B is expected to
  release one flawed report.
- **Arm C (Student):** unknown, which is why it is run.
- **Secondary arms:** the base model is expected to show far more incorrect releases. Its 2G result
  was 2/31 at 5/5 with the grammar and 0/31 without.

**Interpretation rule:**
- If arm B and arm C show few incorrect claims for the trained Student, report that honestly: the
  verifier's measured value is then mainly as a safety net, plus what the secondary model shows.
- No re-runs, prompt changes or threshold changes after seeing results.
