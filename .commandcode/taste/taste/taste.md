# Taste
- Prefers fully local / offline tooling: rejects services that need an account or require uploading data (e.g. U-Sleep) and asks for a local alternative instead, even when the online tool is the "standard" choice. Confidence: 0.75
- Willing to accept extra setup friction (separate venv, pip install) if it keeps a dependency local rather than remote. Confidence: 0.6
- Treats privacy as an explicit project decision to be made and closed out (anonymising/hashing record IDs, retention policy for generated run folders), not something to leave as an open caveat. Confidence: 0.65
- Reports status as a compact item → status table, naming what is blocked or deferred and why, and surfaces trade-offs for approval ("I'd use a local alternative instead, if you agree") rather than deciding unilaterally. Confidence: 0.6
- When something fails mid-run, asks directly "what is the problem / what is the error?" — expects a root-cause diagnosis (literal exit code / error decoded, what stage it died in, what side effects like orphaned processes were left) rather than a guessed or hand-waved explanation. Confidence: 0.65
- Wants genuine bugs separated from environmental/blocked items (missing data, resource limits, unavailable hardware) so effort goes to the right place. Confidence: 0.55
- Expects new work to be additive and non-invasive: when adding a layer (e.g. a UI) to an existing working system, explicitly says "don't disturb the current system" — wants it built alongside in its own isolated location that only imports/calls the existing entry points, not editing the existing code. Confidence: 0.7
- When inputs are missing, wants the exact source location spelled out (absolute root folder, subfolder layout, exact filenames) so they can supply the data themselves; prefers a "drop these files here and rerun, no code change" instruction over a vague description of what's absent. Confidence: 0.6
- UI/visual design: avoids gradient/glowy effects entirely and prefers flat, light themes — cream backgrounds with white cards and soft muted accents rather than dark/neon styling. Stated explicitly when the console UI was restyled ("don't use gradient colours, light colours like white and cream"). Confidence: 0.9
- For reports/readmes, wants more than raw results: explicitly asks for what was done, what the results show, and why they matter ("what does they show and how are they important"), i.e. interpretation and significance alongside the numbers. Confidence: 0.7
- For a report/journal, prefers to supply figures/images themselves and wants the assistant to write the text with figure/table placeholders ("just create the writing part then i will do the figure and images"). Confidence: 0.6
- Wants project documentation grounded in the actual work performed: when handed a generic template-style document (e.g. a weekly log of planned/pending items), corrects it to "it should be of the works we did in the project" and expects the real experiments, results and numbers, not placeholder content. Confidence: 0.6
- When a technical output is correct but hard to read, wants a plain-language summary block appended below it that interprets it, plus concrete suggestions/actions — not a rewrite of the underlying report ("the report is fine but it is difficult to understand so also generate a small summary below the report section that analyses the report and gives the summary and also the suggestion"). Confidence: 0.65
- Prefers deliverables kept short and in simple, plain language — wants content broken into a small number of points (e.g. 3) rather than dense prose ("keep in 3 points in simple terms"). Confidence: 0.55
